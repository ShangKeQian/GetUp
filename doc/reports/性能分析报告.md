# GetUp 性能分析报告

> 分析日期：2026-07-29 · 方法：源码审查 + 真机实测（Windows，Python 3.13.7）
> 实测环境：应用真实运行 60 秒采样 + 独立性能探针（模型加载/摄像头/推理/泄漏循环各项微基准）

---

## 一、结论摘要

| 关注项 | 结论 | 风险等级 |
|---|---|---|
| GPU 占用异常偏高 | **不存在**。空闲/常规运行 GPU 引擎占用实测 0% | 无 |
| 渲染管线 / 着色器 / 纹理 | **不适用**。全部为 Qt CPU 光栅绘制，无着色器、无纹理管线 | 无 |
| 内存泄漏 | 推理循环无泄漏；**检测器反复重建有 ~0.6 MB/次的轻微泄漏** | 低 |
| 卡顿 / 无响应 | **存在真实风险**：摄像头打开阻塞 1.5–2.5 s，叠加主线程 `join(timeout=3)` 可致 UI 冻结最长 3 s | **中** |
| 启动性能 | import + 模型加载 + 首次开摄像头合计约 5 s，其中摄像头占一半 | 低-中 |
| 常驻内存 | 231 MB，偏高但为依赖库（MediaPipe/OpenCV/PySide6）常驻，稳定不增长 | 低 |

## 三、问题清单（按严重度排序）

### 问题 1（中）：摄像头打开阻塞 tick 线程 1.5–2.5 s

**位置**：`detectors/camera.py` `_ensure_open()` → `check_once()` 锁内执行。

DSHOW 后端打开摄像头实测需 1.5–2.5 s，且发生在 `CameraDetector._lock` 锁内、tick 线程上。触发场景：
- 休眠唤醒后首次检测（休眠时 `release()` 了摄像头）；
- 连续 3 次读帧失败后自动重开；
- **摄像头被其他应用独占时**：每 5 秒尝试打开一次、每次阻塞 ~1.5–2.5 s —— tick 线程近一半时间在阻塞，托盘/倒计时更新出现"跳秒"。

**复现条件**：用相机应用（或视频会议软件）占住摄像头，等 GetUp 键鼠空闲超 5 s 触发摄像头检测，观察托盘 tooltip 倒计时跳秒。

**优化建议**：
1. 打开失败时做指数退避（5 s → 30 s → 120 s），而不是固定每 5 s 重试；
2. 或将"打开摄像头"放到独立一次性线程，`check_once` 在未就绪时直接返回 None，不在 tick 路径上等待。

### 问题 2（中）：主线程 `join(timeout=3)` 可致 UI 冻结最长 3 秒

**位置**：`main.py` `_toggle_detection()` L131、`_restart_detection()` L250、`_quit()` L303 —— 三处都在 **Qt 主线程**（托盘菜单/保存按钮回调）执行 `old_thread.join(timeout=3)`。

若此刻 tick 线程恰好卡在摄像头打开（问题 1 的 1.5–2.5 s 阻塞）里，主线程会同步等待，**整个 UI（托盘菜单、设置窗口、遮罩）无响应最长 3 秒**。

**复现条件**：摄像头被占用（重试打开进行中）时，点击托盘"暂停监控"或在设置窗口点"保存设置"。

**优化建议**：把"等待旧线程退出 + 关闭旧检测器"整体移到后台线程完成；主线程只翻转状态标志并立即返回。

### 问题 3（低）：检测器反复重建的轻微内存泄漏（~0.6 MB/次）

**实测**：MediaPipe `FaceDetector` 创建/`close()` 循环 10 次净增 6.4 MB（C++ 侧资源未完全归还，属 MediaPipe 已知行为）。

当前代码在以下时机重建整套 `PresenceDetector`（含模型加载）：
- 每次"暂停监控"（`_toggle_detection` 暂停分支**立即**重建一个新检测器备用）；
- 每次"保存设置"。

**复现条件**：反复暂停/恢复监控 100 次，观察 RSS 增长约 60 MB 且不回落。

**优化建议**：
1. 暂停时**不要**立即重建检测器，延迟到"恢复"时再创建（还能省下暂停期间白白占用的模型内存和 276 ms 加载）；
2. 设置保存时若 `camera_index`/`sleep_timeout` 未变化，复用现有检测器实例，只更新参数。

### 问题 4（低）：启动时后台枚举摄像头与检测线程抢设备

**位置**：`main_window.py` `_cache_cameras()` 在 `__init__` 中即启动，逐个试开 index 0–9（DSHOW 打开失败也常耗时 1 s+，全程可达 10–30 s）。

DSHOW 设备通常独占，枚举线程打开 camera 0 时，检测线程的 `check_once` 会读帧失败 → 触发"失败 3 次重开"路径 → 放大问题 1。

**优化建议**：改为首次打开设置窗口时才扫描（惰性），并跳过当前正在使用的 index；或枚举只到 `max_index=4`。

### 问题 5（提示级）：其他小项

- **托盘菜单全量重建**：`_build_menu()` 在每次在位状态翻转时重建 QMenu 并重新解析样式表。频率低、开销小，但若菜单正打开会被替换（体验问题而非性能问题）。可改为持有 QAction 引用只改文本/使能态。
- **常驻内存 231 MB**：主要是 mediapipe(+57 MB import) + OpenCV + PySide6 的固定成本，运行期稳定不增长，不构成泄漏；若在意可评估用 ONNX Runtime + 轻量人脸模型替代 MediaPipe（可省约 100 MB）。
- **稳定性顺带发现**：`_wake_from_sleep()` 无锁读取 `self._detector`，而 `_restart_detection()` 期间它会被置为 `None`——竞态窗口内点"唤醒"会抛 `AttributeError`。建议加锁快照。

## 四、针对提问的逐项回答

1. **GPU 占用率是否异常偏高？** 否。实测 GPU 引擎占用为 0%。本应用无 GPU 渲染路径：MediaPipe Tasks Python 用 CPU 推理，Qt QPainter 为 CPU 光栅化，唯一接触 GPU 的是 DWM 窗口合成（遮罩 300 ms 淡入动画），可忽略。
2. **是否存在内存泄漏？** 主循环（读帧 + 推理 ×100）实测无泄漏；唯一泄漏点是检测器重建（~0.6 MB/次），仅在频繁暂停/恢复或反复保存设置时缓慢积累（问题 3）。摄像头、pynput 监听器释放逻辑正确。
3. **GPU 高负载场景下是否会崩溃/卡顿/无响应？** 外部 GPU 高负载（如游戏）不影响本应用（无 GPU 依赖），最多淡入动画掉帧。真正的无响应风险来自 CPU/IO 侧：摄像头打开阻塞 + 主线程 join（问题 1+2），最长可冻结 UI 3 秒。
4. **渲染管线 / 着色器编译 / 纹理加载？** 不适用。无着色器编译、无纹理资源。渲染热点仅为每秒一次的 260×260 环形进度条重绘与托盘图标 QPixmap 绘制，实测整机 CPU 平均 0.2%，无瓶颈。

## 五、优化优先级建议

| 优先级 | 动作 | 预期收益 |
|---|---|---|
| P0 | 主线程 join/close 移到后台线程（问题 2） | 消除 UI 冻结风险 |
| P1 | 摄像头打开失败指数退避（问题 1） | 消除跳秒卡顿、降低占用冲突 |
| P1 | 暂停时延迟重建检测器（问题 3） | 消除泄漏点 + 省 276 ms/次 + 降低暂停态内存 |
| P2 | 摄像头枚举惰性化（问题 4） | 消除启动期设备抢占 |
| P3 | 托盘菜单增量更新、`_wake_from_sleep` 加锁 | 体验与稳定性 |
